# Bake-off — 2026-08-17

Greybeard (`--dry-run --force`, Bedrock: Opus 5 lenses / Haiku 4.5 verify) vs the
actual review history of five merged GovOrch PRs. Per-PR scoring by independent
judge agents that verified disputed claims against the code (several by
executing it). No comments were posted.

## Verdict

- **Precision: perfect.** 0 false positives posted across all five PRs. The one
  confirmed finding (committed test-report files in nexus#1128) is real and still
  on master.
- **Recall: gated by our own verifier, not by the lenses.** The lenses generated
  24 candidates including genuinely real issues on 4/5 PRs — then the Haiku
  verifier killed 23 of them, including the single best find of the whole set:
  the nexus#1128 circular import (`dbpass → services/iam/__init__ → account_service
  → dbpass`, the "tests/auth-alone gotcha"), rejected twice with **factually wrong
  Python import semantics**. Judges logged 5 wrong rejections, all Haiku
  rationalizations.
- **Head-to-head vs CodeRabbit** (oracle#17): loss, 0–3. All three misses are one
  blind spot: no CI/workflow-security lens (job-scoped `id-token`,
  `secrets: inherit`, nginx location shadowing). CodeRabbit's top-severity claim
  (arm64 image "incompatible") was wrong for this ARM64 cluster, consistent with
  its noise reputation.
- **Vs humans** (nexus#1127): rough parity on substance — Greybeard surfaced 2 of
  the 3 substantive human findings as candidates (verifier killed both as
  judgment calls) and found 1 real docstring inaccuracy the humans missed.
- **Coverage story:** 2 of 5 PRs merged with effectively no review at all
  (CodeRabbit rate-limited). Greybeard produced real findings on both.

## Fixes, ranked (Phase 2)

1. **Verifier tier upgrade** — Haiku demonstrably invents wrong rejection
   rationales. Move verification to the lens model at low effort (or Sonnet 5).
   Verify calls are short; the cost delta is small and it un-suppresses the
   pipeline's best work.
2. **Pack-size cap + degraded-mode honesty** — packs over the verify model's
   context silently kill all verification and still render "You shall pass."
   Cap/truncate the pack per tier, and when verification is unavailable, say so
   in the comment (findings posted as unverified or an explicit degraded notice)
   — never silent.
3. **Add a CI/infra lens** — workflows, Dockerfiles, nginx/proxy config,
   permissions scoping. Erases the entire oracle#17 loss.
4. **Verifier prompt fix** — several rejections *conceded the claim was true*
   ("the docstring is stale… but out of scope") and rejected anyway; forbid
   rejecting findings whose factual claim the verifier confirmed, and stop
   citing PR-body "known gap" notes as grounds for rejection.

## Round 2 — same five PRs, after the fixes

Re-run with the strong verifier (lens model at low effort), the verifier prompt
rules, the ci-config lens, the pack cap, and loud degradation. Confirmed posts
went 1 → 0, but the story is the opposite of a regression:

- **Verification quality fixed.** Rejection reasoning is now factually careful.
  The verifier *confirmed as true* the committed test-report files (nexus#1128),
  the nginx gzip_types gap and `secrets: inherit` forwarding (oracle#17), and
  all four dead-code/false-comment findings on oracle#231 — no more invented
  import semantics.
- **The ci-config lens closed the CodeRabbit gap.** All three real oracle#17
  baseline findings now surface as candidates (they never surfaced in round 1).
- **Degradation is loud.** The one unverifiable candidate (a truncated verify
  response) produced a "Verification degraded" warning instead of a silent
  "You shall pass."
- **The bottleneck moved to the gate.** The 0-100 rubric folds importance into
  confidence: verified-true minor findings score 40-78 and die at the flat
  ≥80 gate. That is now a policy choice, not a defect — open question: keep
  "only big stuff posts", or a severity-aware gate (blocker/gap ≥80,
  verified-true nits ≥60 into a collapsed "Minor notes" section), which on this
  suite posts ~8 real findings and 0 false ones.
- The nexus#1128 circular import remains the hardest case: the verifier now
  argues (defensibly, from CI signals in the pack) that the failing import
  order "doesn't occur in practice" — it did, once, for the team. Zero-tool
  verification has a ceiling; a bounded exec-check tool is the Phase 3+ answer.

## Round 3 — live vs Greptile, 2026-08-18 (PR #12)

Greptile was installed on this repo mid-development, making PR #12
(ops & reliability, v1.2.0) the first **live** head-to-head: both reviewers
posting real comments on the same PR across the same push sequence, final head
`4e070f2`. Unlike rounds 1–2 this was not a dry-run replay — every finding from
either bot was fixed or rebutted before merge.

### Scoreboard

|  | Greybeard | Greptile |
| --- | --- | --- |
| Real findings | **6** | 2 unique + 1 duplicate |
| False positives | 0 | 0 |
| Final verdict on head | "You shall pass." | 5/5 |

Greybeard's six included the two ops-semantics catches that shaped the release:
skips resetting the failure streak (a draft/bot skip exercises none of the LLM
path, so it could have masked a dead pipeline indefinitely — now only completed
runs reset `consecutive_failures`), and superseded runs losing their spend
telemetry when a newer push aborted them mid-flight.

Greptile's two unique catches were real and both taken:

- **Superseded double-count race** — `abort()` is a request, not a guarantee; a
  task already past its last await completes its own accounting anyway, so
  recording "superseded" at the abort site can count one run twice. Fix: await
  the old `JoinHandle` — `Err(cancelled)` is the only honest signal the run
  died unaccounted.
- **Sink consistency** — superseded runs missing from the JSONL sink, plus
  hardcoded `action`/`force` metadata on the superseded path.

Its first P1 (inflight leak on cancellation) duplicated a finding Greybeard had
posted a round earlier. Zero false positives from either side.

### Feature comparison

Where Greybeard matches or beats Greptile:

| Dimension | Greptile | Greybeard |
| --- | --- | --- |
| Noise control | filtering + learned suppression | adversarial per-finding verification + confidence-banded gate — **measured 0 false positives across every bake-off round**; this is Greybeard's core identity |
| Parallel review | "agent swarm" | 6 parallel lenses + pipelined verifiers — same idea, deterministic and cache-optimized (~$1–3/review, 1–4 min) |
| History awareness | graph of code | blame + prior-PR-comment lenses — temporal context Greptile doesn't emphasize; caught docstring-vs-history issues humans missed |
| Ownership & compliance | cloud, or vendor-shipped self-hosted | fully ours: our VPC, Bedrock (data never leaves the account), our persona, gate policy in a doc we control — for gov work a structural advantage, not a feature |
| Cost | $30/seat + usage credits | per-review tokens, no seats, no procurement |

Where Greptile is genuinely ahead:

1. **Whole-codebase context.** Its graph index (files/functions/dependencies)
   lets reviews assess impact beyond the diff. Greybeard's pack is deep on the
   change but blind past changed files — our biggest architectural gap, and
   exactly why the nexus#1128 circular import stays the hardest case.
2. **Persistent learning.** Greptile accumulates team standards from PR
   comments over time. Our prior-feedback lens reads past comments per file at
   review time — similar signal, nothing accumulates yet (Phase 2 feedback
   loop / `.greybeard.md`).
3. **Test execution (TREX).** Writes and runs tests per PR in a sandbox. We
   deliberately scoped out re-running gates; the planned bounded exec-check
   verifier is a much smaller cousin.
4. **The fix loop** — *bridged since v1.1.0*: the `greybeard-loop` skill is our
   `/greploop` equivalent (marker v2 findings → fix/rebut → webhook re-review),
   proven twice in prod before this round.

### Takeaways

- Precision parity at 0 FPs each; Greybeard led on recall 6 vs 2 on this PR.
- The gaps that matter map 1:1 onto the existing Phase 2 backlog (repo-wide
  context, feedback loop, exec-check) — the bake-off changed priorities, not
  the plan.
- Greptile stays installed; every future PR is a free continuation of this
  bake-off during the observe window.
